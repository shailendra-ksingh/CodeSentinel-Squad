# CodeSentinel Squad

## Multi-Agent Code Review Assistant for Java/JEE

CodeSentinel Squad is a Java-based code review assistant that combines **static analysis** with a small group of **specialist AI agents**.

The idea is simple:

> **Analyze → Route → Specialize → Critique → Remember**

Instead of asking one AI agent to review everything, CodeSentinel first finds evidence in the source code and then sends relevant work to specialist agents.

---

## 1. What Does CodeSentinel Do?

CodeSentinel reviews a Java source file for common code-quality problems such as:

- Security issues
- Error handling problems
- Resource leaks
- Null-safety risks
- Missing documentation
- Architecture concerns

Based on the findings, the Coordinator decides which specialist agents should run.

The system can also:

- Generate JUnit 5 tests
- Review generated tests using a Critic Agent
- Ask the Test Agent to revise tests when the Critic finds a problem
- Remember findings from previous reviews
- Run in Safe Mode without an AI API key

---

## 2. How It Works

```text
                 Java Source
                      |
                      v
              +---------------+
              | Static        |
              | Analyzer      |
              +-------+-------+
                      |
                      v
               Finding Evidence
                      |
                      v
              +---------------+
              | Coordinator   |
              +-------+-------+
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
      Security      Testing      Docs
        Agent        Agent      Agent
                      |
                      v
                   Critic
                  /      \
                 /        \
           APPROVE       REVISE
                            |
                            v
                       Test Agent

                      |
                      v
               Architecture
                  Agent

                      |
                      v
                 Final Report
                      |
                      v
                   Memory
````

The important part is that **the findings drive the routing**.

Agents are not blindly executed for every Java class.

## 3. Specialist Agents

### Coordinator Agent

The Coordinator is responsible for routing.

It looks at the findings and decides which specialists are relevant.

For example:

```text
Security finding
      ↓
Security Agent

Documentation finding
      ↓
Documentation Agent

Architecture finding
      ↓
Architecture Agent

Testable finding + public method
      ↓
Test Agent
```

---

### Security Agent

Handles security-related findings.

It explains:

* Why the issue matters
* Possible security impact
* Example risk
* Suggested remediation

---

### Test Generation Agent

Generates JUnit 5 tests for issues that can reasonably be tested.

The Test Agent is only dispatched when:

1. The class contains a public method
2. There is a relevant testable finding

This avoids generating tests for every Java file.

---

### Documentation Agent

Handles documentation findings.

It can generate Javadoc and a simple class summary.

It runs only when the Static Analyzer reports a documentation issue.

---

### Architecture Agent

Handles higher-level design concerns.

For example, the current prototype can identify a class that is unusually large or has many public methods.

This is a **heuristic signal**, not a replacement for a full architecture analysis.

---

### Critic Agent

The Critic reviews tests generated by the Test Agent.

It performs simple local checks first:

* Is a Java class present?
* Is there an `@Test` method?
* Is there a meaningful assertion?
* Are braces balanced?

It then performs a semantic review using the AI service.

The flow is:

```text
Test Agent
    |
    v
Generated Test
    |
    v
Critic
    |
    +---- APPROVED
    |
    +---- REVISE
             |
             v
        Test Agent
```

The current prototype allows one revision.

---

## 4. Static Analysis First

CodeSentinel does not start by sending the entire source file to an AI model.

The first step is deterministic analysis.

```text
Java Source
     |
     v
Static Analyzer
     |
     v
Findings
     |
     v
Coordinator
```

This gives the specialist agents a common set of evidence.

The Static Analyzer is intentionally lightweight and pattern based.

It is not intended to replace tools such as SonarQube, SpotBugs, PMD, or compiler-level analysis.

Its purpose is to provide a fast first pass and useful routing signals.

---

## 5. Memory

CodeSentinel keeps a small local history under:

```text
memory/
```

The memory stores finding information for a class.

It does **not** store the source code.

When the same issue signature appears again in a later review, CodeSentinel reports it as a recurring finding.

For example:

```text
First review:
Security - hardcoded password

Second review:
Security - hardcoded password
```

The second review can report:

```text
Detected again in the current review
```

The recurrence check uses the finding category and description.

The line number is intentionally not used because code can move between reviews.

---

## 6. Safe Mode

An Anthropic API key is **not required** to run the basic review.

If:

```text
ANTHROPIC_API_KEY
```

is not configured, CodeSentinel runs in **Safe Mode**.

In Safe Mode:

```text
Java Source
     |
     v
Static Analyzer
     |
     v
Findings
     |
     v
Memory + Report
```

No AI API call is made.

This gives the project a useful offline fallback.

## 7. Technology

The project intentionally uses a small technology stack:

* Java 17
* Maven
* JUnit 5
* JDK `HttpClient`
* Anthropic Claude API
* Local file-based memory

There are no additional AI frameworks or runtime dependencies.

Install:

* Java 17 or later
* Maven 3.8+

Check Java:

```bash
java -version
```

Check Maven:

```bash
mvn -version
```

An Anthropic API key is required only for full AI mode.

From the project root:

```bash
mvn clean package
```

The executable JAR is created at:

```text
target/codesentinel.jar
```

## 10. Configure AI Mode

### Windows

```powershell
setx ANTHROPIC_API_KEY "your-api-key-here"
```

Open a new terminal after using `setx`.

### macOS / Linux

```bash
export ANTHROPIC_API_KEY="your-api-key-here"
```

Do not hardcode the API key in source code.

# 13. Output

After a review, the project creates an `output` directory.

Typical output:

```text
output/
├── review.md
├── SampleVulnerableServiceTest.java
└── SampleVulnerableService.java
```

The exact generated files depend on which specialist agents were dispatched.

The `review.md` report contains:

* Review summary
* Findings
* Recurring findings
* Dispatched agents
* Skipped agents
* Agent output
* Critic transcript
* Warnings

The `memory` directory contains the local review history.

# 15. Example Workflow

A typical review looks like this:

```text
1. Read Java source
        |
        v
2. Static Analyzer
        |
        v
3. Create findings
        |
        v
4. Coordinator checks relevance
        |
        +---- Security Agent
        |
        +---- Test Agent
        |          |
        |          v
        |       Critic
        |          |
        |      APPROVE / REVISE
        |
        +---- Documentation Agent
        |
        +---- Architecture Agent
        |
        v
5. Generate report
        |
        v
6. Save finding history
```

# 16. Failure Handling

A specialist failure should not stop the complete review.

For example:

```text
Security Agent
      |
      X
    Failed
      |
      v
Warning recorded
      |
      v
Other agents continue
      |
      v
Final report
```

The warning is included in the report so that the developer knows manual review may still be required.

---

# 17. Current Limitations

CodeSentinel is a focused prototype.

Current limitations include:

* Static analysis is pattern/regex based
* One Java file is reviewed at a time
* Generated tests are reviewed but are not automatically compiled
* AI mode requires network access
* The semantic Critic currently uses the configured Claude service
* The system is not intended to replace enterprise tools such as SonarQube or SpotBugs

These limitations are intentionally kept visible rather than hiding them behind broad claims.

---

# 18. Future Improvements

Possible future extensions include:

* Compile generated tests automatically
* Review complete multi-module projects
* Review pull-request diffs
* CI/CD integration
* SonarQube or SpotBugs integration
* Persistent review history
* Independent model for Critic review

These are future improvements and are not required for the current prototype.

---

# 19. The Core Idea

CodeSentinel Squad is built around a simple idea:

> **Don't ask one AI to do everything. Give each agent a clear job, let another agent review the result, and remember what happened before.**

The architecture is kept small:

```text
Evidence
   ↓
Reasoning
   ↓
Critique
   ↓
Memory
```

The goal is to keep the system simple and to make the code review process **more focused, explainable and repeatable**.
